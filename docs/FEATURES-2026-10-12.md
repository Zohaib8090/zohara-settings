# USB drives, SD cards and external disks (2026-10-12)

Settings > Bluetooth & devices > **USB & storage devices**. Files: `src/backend/drives.rs` (logic, UDisks2 calls, tests), `src/pages/drives.rs` (screens),
the group is added in `src/pages/bluetooth.rs`. `PKGBUILD` depends on `udisks2` (optdepends ntfs-3g, exfatprogs, dosfstools); `zohara/zohara-profile/packages.x86_64` lists `udisks2`.

## What it does
* Lists USB sticks, external disks and SD cards (follows plugging and unplugging, 3 s while the page is open). Each opens a page: partitions with size and use,
  Open / Mount / Unmount, **Rename**, **Check and repair**, **Format** (exFAT, FAT32, NTFS if `mkfs.ntfs` exists, ext4, Btrfs; quick or overwrite with zeros),
  **Erase the whole drive** (new partition table + one partition: MBR for small drives with exFAT/FAT32/NTFS so old TVs and cameras read them, GPT otherwise), **Safely remove**
  (unmount, eject, power off) and **Make a bootable USB drive** (ISO or `.img`, with a read-back check, progress and Stop).
* Internal disks are never offered (a row links to the Storage page). A disk that holds anything the running system uses (`/`, `/boot`, `/home`, `/var`, `/usr`, swap, the live image in
  `/run/archiso`) is locked in every mode, so the stick Zohara itself was started from can't be erased. A write-protected drive says so.

## Safety rules (all enforced in `backend/drives.rs`, with tests)
1. Only `Kind::UsbStick | ExternalDisk | SdCard` (and `Image`, a loop device, only when `ZOHARA_DRIVES_SHOW_IMAGES=1`) can be changed.
2. Before every destructive step the drive is looked up again and must have the same path, size, model, serial and WWN as when the person confirmed (`still_the_same`),
   and must still be changeable. Swapped or removed drives stop the job.
3. Every destructive dialog names the drive, lists what is on it and needs `ERASE` typed.
4. PolicyKit decides (UDisks2): format, rename, check, mount, eject are allowed for the logged-in user on removable drives without a password (`modify-device`); **writing an image needs
   the administrator password** (`open-device` is `auth_admin_keep`), so Settings never writes a disk unattended. Settings never sees the password.
5. Device paths are checked before they reach D-Bus (`block_object_path` only takes `/dev/<letters, digits, _>`).
6. Image writing refuses an image that is bigger than the drive or stored on the drive that is about to be erased.

## How it talks to the system
`lsblk -J -b` (columns in `LSBLK_COLUMNS`) for what is there; UDisks2 over D-Bus through `zbus` on a private single-thread tokio runtime inside the worker thread (`Block.Format`,
`PartitionTable.CreatePartitionAndFormat`, `Filesystem.SetLabel/Check/Repair/Mount/Unmount`, `Drive.Eject/PowerOff`, `Block.OpenDevice` which hands back a file descriptor, `Block.Rescan`).
`interactive: false` adds `auth.no_user_interaction` (used by the tests), so a missing permission is an error, not a password window.

## Facts found by testing on a real system
* **An exFAT name is at most 11 characters** (UDisks refused 14); FAT32 is 11 too and upper case; ext4 16 bytes. The first table said 15 for exFAT: wrong, fixed.
* A loop device (a file made to look like a drive) formats, renames and checks as the normal user; `udisksctl loop-delete` can later ask for the administrator (`NotAuthorizedCanObtain`) when the
  device was mounted or partitioned: it stays until reboot (a harmless leftover from the 2026-10-12 session: `/dev/loop0`, backing file deleted).

* 5 live tests on fake drives (`cargo test backend::drives::live:: -- --ignored --test-threads=1`): list/format/rename/check/erase with both table styles, wrong drive refused, the running system's disk

## Power & battery: Hibernate only when it can work (2026-10-12)

Hibernate and Hybrid sleep are hidden from Power & battery (idle action, lid, power button, critical battery action) unless this computer
has swap at least as big as its RAM **and** a `resume=` option on the kernel command line (`src/backend/hibernate.rs`, 6 unit tests).
Before, the page offered Hibernate on installs that had no swap for it. A Hibernate value already saved stays in the config and shows as
the first entry. Existing installs have no hibernate swap, so they simply lose the choice; new installs can pick "Swap (with Hibernate)"
in the installer (`zohara` `partition.conf`, not yet tested with a real install). Not clicked in a VM.

## Accounts for web apps (added later on 2026-10-12)

Settings > Apps > Apps for websites now has an **Accounts** list above the web apps.

* An **account** is a local browser profile that several web apps can share: sign in to Google once and Gmail, Docs and
  YouTube apps are all signed in. Several accounts keep several Google accounts apart. Nothing is synced to Google or the
  browser vendor. Add, rename and delete accounts from the list; deleting one deletes its sign-ins and puts the apps that
  used it back on their own separate sign-ins.
* Each web app has a **Sign in with** row: *Separate* (the old behaviour, still the default, so existing apps are
  unchanged), a named account, or *Ask each time*.
* *Ask each time* is for a computer more than one person uses. The launcher runs `zohara-settings --webapp <id>`, which
  shows a small window listing the accounts and a **Guest**. A guest's profile lives in `~/.cache/zohara-webapps/guest-<id>`
  and is deleted when the app closes (the chooser process waits for it); it is also wiped at the next guest launch.
* Code: `src/backend/web_accounts.rs` (accounts file `~/.local/share/zohara-webapps/.accounts/accounts.json`, session
  text `""` / `account:<id>` / `ask`, profile paths, window class, 6 tests) and `src/pages/web_apps.rs`.

Rules and limits worth knowing:

* Apps sharing an account run in **one browser process**, so each app cannot pass its own `--class`. The launcher's
  `StartupWMClass` is therefore computed from the address (`chrome-<host>__<path>-Default`). Checked on 2026-10-12 with real
  Chrome: two `--app` windows on one profile got `chrome-example.com__-Default` and `chrome-www.iana.org__domains-Default`.
* *Start in the background* and per-app *Permissions* only work for a separate profile (the minimize rule needs its own
  window class, and permissions are written profile-wide). The editor switches them off for shared and asking apps.
* Each browser keeps its own profile inside an account (`.accounts/<id>/<browser>/profile`; Flatpak browsers under
  `~/.var/app/<id>/data/zohara-webapps/accounts/<id>/profile`), because one profile folder cannot be shared between
  different browsers.

Verified on 2026-10-12 by clicking through a test copy (own session bus and data folder, built from the same commit as
alpha) with real Google Chrome: Add account (button and Enter), Rename, the Sign in with row (Separate / an account / Ask
each time) and the greyed-out Permissions with its reason, Create and Edit (browser and account saved, launcher regenerated),
the list showing "Used by ..." and the account on each app, **two apps on one account opening as two windows of one browser
process with the window classes the launcher expects**, the chooser opening from the Open button, **Work** picked in it
(app opened on the shared profile) and **Guest** picked (temporary profile in `~/.cache/zohara-webapps`, deleted when the
browser closed and the chooser exited), closing the chooser without choosing (nothing opens), deleting an account (Cancel
changed nothing; Delete removed the sign-ins and put both apps back on separate sign-ins with their own launcher), and
removing an app (the account list was untouched). 289 unit tests pass.

Not verified: a real Google sign-in shared by two apps; Brave (see below); Flatpak browsers; "Open when you sign in" with an
asking app; the label wording on a language other than English.

Findings from the test:

* **Brave Origin shows its own welcome page for every brand-new profile**, so the first launch of each new account (and of
  each new separate app) in Brave Origin shows it once, before the site. This is Brave's behaviour, not something this feature
  adds; the test used Chrome for that reason.
* **`--class` has no effect on this Wayland session with Chrome**: an app started with `--class=zohara-webapp-<id>` still got
  the window class `chrome-<host>__<path>-Default`. So the launcher's `StartupWMClass=zohara-webapp-<id>` of *separate* apps
  (older code) does not match their windows with Chrome, and the "Start in the background" KWin rule, which matches
  `zohara-webapp-<id>-bg`, may never apply. Not changed here; check it with Brave on the laptop before relying on it.

### Moving existing web apps to accounts (added 2026-10-12)

Nothing is changed for you: an app made before accounts existed has no `session` in its `app.json`, loads as **Separate**
and keeps working with the sign-ins it has. To share those sign-ins, open the app's settings and press **Create account**
on the row *Keep these sign-ins as an account*. That moves the app's existing browser profile (cookies, logins) into a new
account (`adopt_profile`, which refuses to overwrite a profile already there, falls back to copy-then-delete across disks, and
needs the app closed) and puts the app on it; other apps can then pick the account. Clicked through on 2026-10-12 with an old-format
app holding a fake cookie: the account was created, the cookie was in the new place and unchanged, the old profile folder was
gone, `app.json` and the launcher pointed at the account, and the list showed the account as used by the app. A new unit test
covers the move, the refusal and an app that was never opened. Not tried with a real signed-in browser profile or a Flatpak
browser.
