# USB drives, SD cards and external disks (2026-10-12)

Settings > Bluetooth & devices > **USB & storage devices**. Files: `src/backend/drives.rs` (logic, UDisks2 calls, tests), `src/pages/drives.rs` (screens),
the group is added in `src/pages/bluetooth.rs`. `PKGBUILD` depends on `udisks2` (optdepends ntfs-3g, exfatprogs, dosfstools); `zohara/zohara-profile/packages.x86_64` lists `udisks2`.

## What it does
* Lists USB sticks, external disks and SD cards (follows plugging and unplugging, 3 s while the page is open). Each opens a page: partitions with size and use,
  Open / Mount / Unmount, **Rename**, **Check and repair**, **Format** (exFAT, FAT32, NTFS if `mkfs.ntfs` exists, ext4, Btrfs; quick or overwrite with zeros),
  **Erase the whole drive** (new partition table + one partition: MBR for small drives with exFAT/FAT32/NTFS so old TVs and cameras read them, GPT otherwise), **Safely remove**
  (unmount, eject, power off) and **Make a bootable USB drive** (ISO or `.img`, with a read-back check, progress and Stop).
* Internal disks are never offered (a row links to the Storage page). A disk that holds anything the running system uses (`/`, `/boot`, `/home`, `/var`, `/usr`, swap, the live image in
  `/run/archiso`) is locked in every mode, so the stick Zohara itself was started from can't be erased. A write-protected drive says so.

## Safety rules (all enforced in `backend/drives.rs`, with tests)
1. Only `Kind::UsbStick | ExternalDisk | SdCard` (and `Image`, a loop device, only when `ZOHARA_DRIVES_SHOW_IMAGES=1`) can be changed.
2. Before every destructive step the drive is looked up again and must have the same path, size, model, serial and WWN as when the person confirmed (`still_the_same`),
   and must still be changeable. Swapped or removed drives stop the job.
3. Every destructive dialog names the drive, lists what is on it and needs `ERASE` typed.
4. PolicyKit decides (UDisks2): format, rename, check, mount, eject are allowed for the logged-in user on removable drives without a password (`modify-device`); **writing an image needs
   the administrator password** (`open-device` is `auth_admin_keep`), so Settings never writes a disk unattended. Settings never sees the password.
5. Device paths are checked before they reach D-Bus (`block_object_path` only takes `/dev/<letters, digits, _>`).
6. Image writing refuses an image that is bigger than the drive or stored on the drive that is about to be erased.

## How it talks to the system
`lsblk -J -b` (columns in `LSBLK_COLUMNS`) for what is there; UDisks2 over D-Bus through `zbus` on a private single-thread tokio runtime inside the worker thread (`Block.Format`,
`PartitionTable.CreatePartitionAndFormat`, `Filesystem.SetLabel/Check/Repair/Mount/Unmount`, `Drive.Eject/PowerOff`, `Block.OpenDevice` which hands back a file descriptor, `Block.Rescan`).
`interactive: false` adds `auth.no_user_interaction` (used by the tests), so a missing permission is an error, not a password window.

## Facts found by testing on a real system
* **An exFAT name is at most 11 characters** (UDisks refused 14); FAT32 is 11 too and upper case; ext4 16 bytes. The first table said 15 for exFAT: wrong, fixed.
* A loop device (a file made to look like a drive) formats, renames and checks as the normal user; `udisksctl loop-delete` can later ask for the administrator (`NotAuthorizedCanObtain`) when the
  device was mounted or partitioned: it stays until reboot (a harmless leftover from the 2026-10-12 session: `/dev/loop0`, backing file deleted).

## Tests
* 25 unit tests (`cargo test backend::drives::tests`): kinds, locking, live-stick lock, labels, tables, swapped-drive guard, device-path guard, image checks, copy/verify/cancel.
* 5 live tests on fake drives (`cargo test backend::drives::live:: -- --ignored --test-threads=1`): list/format/rename/check/erase with both table styles, wrong drive refused, the running system's disk
  refused, an image that is too big refused, writing refused without a password (and a full write check with `ZOHARA_LIVE_INTERACTIVE=1`, which shows the password window).
  **Never run `cargo test live_ -- --ignored` without a module path:** it runs every live test of the whole project against the real desktop (see GOTCHA).

## Verified by clicking (2026-10-12, with the owner away): fake drives, my own test copy of Settings
Run as `ZOHARA_DRIVES_SHOW_IMAGES=1 dbus-run-session -- target/debug/zohara-settings --page "Bluetooth & devices"` (own session bus, so it runs beside the installed copy), with fake
mouse and keyboard clicks. Seen working, each checked against `lsblk` afterwards: the drive list (two fake drives, bootable row, link to the Storage page), a drive page, Mount, Unmount,
**Rename** (a too-long name is refused with the reason; a valid one changes the real label), **Check and repair** ("No problems found"), **Format** (ext4 with a name: the system showed
ext4 + the name; Format stays disabled until ERASE is typed, case does not matter), **Erase the whole drive** (FAT32 + lower-case name: MBR table, one partition, name upper-cased),
**Safely remove** ("It is safe to unplug the drive", page closes), **Make a bootable USB drive** (image chosen in KDE's file picker with the .iso/.img filter, drive preselected, ERASE needed;
Write asked for the administrator password as designed, cancelling it gave "The change wasn't allowed..." and reset the form).

Bugs found and fixed by that run: the group heading was missing (`&` must be `&amp;` in a PreferencesGroup title), the Rename dialog did not put the cursor in the field, a refused name gave no reason,
"exfat" shown in lower case in the list of what is lost, "A MBR". Also tightened: an internal SATA disk that the board reports as hot-pluggable is now treated as internal (only USB, removable media and SD cards count as outside).

## Not verified
* **Nothing was tried with a real USB stick, SD card or external disk.** (A loop-device partition asks for the administrator password to rename it, a real removable drive should not: not confirmed.)
* The bootable write **with the real password**, its progress bar and Stop, and the read-back check. Only the refusal path, the copy/verify code (unit tests) and the D-Bus method shape were checked.
* Not built: drive health (SMART), a setting for what happens when a drive is plugged in, formatting internal disks.

## Power & battery: Hibernate only when it can work (2026-10-12)

Hibernate and Hybrid sleep are hidden from Power & battery (idle action, lid, power button, critical battery action) unless this computer
has swap at least as big as its RAM **and** a `resume=` option on the kernel command line (`src/backend/hibernate.rs`, 6 unit tests).
Before, the page offered Hibernate on installs that had no swap for it. A Hibernate value already saved stays in the config and shows as
the first entry. Existing installs have no hibernate swap, so they simply lose the choice; new installs can pick "Swap (with Hibernate)"
in the installer (`zohara` `partition.conf`, not yet tested with a real install). Not clicked in a VM.
